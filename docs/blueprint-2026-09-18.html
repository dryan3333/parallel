平行线蓝图

「平行线」是一家两人 marketing 小公司的轻量工作台：以「客户」为根，每个客户下面挂 campaign（现有项目）、文档（brief / SOP / 纪要 / 日志 / 复盘 / 提案）和文件台（合同、报价、月报、素材，上传件与外链同列）；今天 / 本周 / 看板 / 提醒继续做执行层，Miranda 的每日 SEO/SEM 巡检变成可勾选的例行任务并在客户页一排链接 chips 上完成、落一行日志，Sara 的提案 / PRD / SOP 就写在客户或项目下。它借 Notion 的「文档挂在对象上」、Jira 的「任务 + 阶段」、Slack 的「提醒即沟通」，但只用 Markdown、固定枚举和三张新表在现有 React + Supabase + GitHub Pages 代码上演进，免费额度内够两个人用两年。

胜出的骨架是「以客户为根的文档中枢」，再把执行流水线和文件台构想里评审认可的部分嫁接进来；沟通流构想被判定为会引入噪音，只保留「提醒即沟通」这一条。

原则

  • 客户为根、文档必须挂靠：所有文档和文件只能从客户页 / 项目页进入，新建时必须选挂靠（客户 / 项目 / 工作区 SOP 三选一，由 check 约束保证），没有页面树、没有文件夹，从结构上防止空洞 wiki 与网盘化。
  • 轻的判据（每个新功能上线前逐条打勾）：不新增 npm 依赖；一个阶段最多新增 3 张表；整个蓝图只新增 1 个顶级导航（客户）；新表 RLS 只调用现有 is_ws_member / is_ws_owner / can_edit_project 三个基元；不做块编辑器、富文本、自定义工作流、自由标签；Miranda 不需要 Sara 讲解、1 分钟内会用；数据层沿用「全量拉取 + 整表重拉」，唯一例外是 docs.body 按需拉。
  • 先修再建：Realtime DELETE 不同步、loadMembership 取最早工作区、Android 通知报错、整行 upsert 互相覆盖这四个现有漏洞在建 clients / docs / files 之前先修，否则新对象只会放大旧问题。
  • 数据先于界面：客户档案、渠道、看板链接用 seed 脚本一次灌进去再上线客户页；日志习惯先跑两周再放周报按钮；空页面等于没上线。
  • 执行层不动、只加回链：今天 / 本周 / 看板 / 任务的核心交互与 status 枚举不变，新对象通过 client_id / doc_id / file_id 回链接进来；产品线项目 client_id 为空时一切照旧。
  • 免费额度是硬约束、界面把规则写明：单文件 ≤ 20MB、图片默认压 webp、视频与设计源文件一律外链、用量条 80% 变黄；文件台不是网盘，是「找得到的交付物清单」。

文件台

存储

Supabase Storage 新建一个私有 bucket `files`（不勾 public，file_size_limit 设 20MB 留余量），对象路径固定 `{workspace_id}/{file_id}-{safe_name}`，首段就是工作区 id。storage.objects 三条策略：select / insert 要求 bucket_id='files' and is_ws_member((storage.foldername(name))[1]::uuid)；delete 再加 (owner_id = auth.uid()::text or is_ws_owner(...))（owner 列已弃用，用 owner_id）。元数据在 public.files（kind upload|link、name、path、url、mime、size、category、period、client_id/project_id/doc_id/task_id、uploaded_by），加入 supabase_realtime 并 replica identity full。上传顺序：前端校验 → 图片压缩 → storage.upload(path, blob, {upsert:false}) → insert files 行；DB 失败则 storage.remove 回滚。删除反序：先 remove([path]) 再 delete 行，remove 失败不删行并 toast。所有 storage 调用收口在 src/lib/upload.ts 与 store 两处，日后换 R2 / Pro 只改这两处。signedUrl 在内存 Map 缓存 50 分钟，同一会话不重复签。

组织方式

不做文件夹。四个维度筛选：客户 / 项目 / 所属文档或任务 / category（合同报价 contract、brief、素材 asset、交付物 deliverable、报告数据 report、其他），report 类带 period（YYYY-MM）驱动客户页「报告时间线」（一月一格，缺月灰格「未上传」）。上传时归属从上下文自动继承（在任务弹窗传 → 补 task/project/client；在项目页传 → 补 project/client），UploadDialog 只留 category 一个必选、名称默认文件名。一个 FilesPanel 组件带 props {clientId?, projectId?, docId?, taskId?} 复用到客户页、项目页、文档页、任务弹窗；「客户」页的「文件」seg 是它的无过滤全量模式。上传件与外链同表同列，只是图标不同、外链无大小。产品线项目的文件 client_id 为空，全量视图里归「内部」。

权限

读 / 上传 = 工作区成员（不叠加 can_edit_project，Miranda 必须能传自己负责客户的文件）；删除 = 上传者或 owner；改元数据（名称 / category / 归属）= 上传者或 owner。不做文件级权限、不做客户级成员隔离。这与 README 现有「按项目分权」口径不同，需 Sara 拍板（D1）并更新 README。storage 策略上线前用第二个账号（Miranda）实测：能看、能传、不能删别人的；再用第三个测试账号验证跨工作区读不到。

分享

缓解：E1-S5 的 keepalive.yml 扩成「保活 + 每周导出」：service_role key 进 GitHub Secrets，每周 `select *` 六张表导出 JSON 作为 artifact 保留 90 天；clients 删除改为归档（archived=true）不做物理删除，或 docs.client_id 改 on delete set null；README 明确写「合同/报价原件在 Drive 保留一份，文件台是索引不是唯一副本」。
第一阶段范围过大，Miranda 的每日闭环上线太晚，日志习惯建立不起来
整套蓝图约 150 小时，第一阶段 90 小时；Sara 是兼职开发（同时管四条业务线），3 周内做不完，而蓝图自己的前提是「日志习惯先跑两周再放周报」。如果客户页要等文档页、MdEditor、docs 九种 kind 全部完成才上线，Miranda 会在这期间继续用微信+Drive，系统上线时已经没有使用惯性，客户页空着就等于没上线。
缓解：按 too_heavy 最后一条切出 35 小时最小闭环：客户表 + 客户页（链接 chips + Markdown 备注）+ 例行任务 + 记一笔日志，一周内让 Miranda 每天早上「打开今天页 → 勾例行 → 点客户链接 → 记一笔」跑起来；两周后看 log 文档条数决定是否继续 E3/E4。数据先于界面：客户由 Sara 手录，不写 seed 脚本。
在没有测试的 1000 行代码上先重构 store 再叠三张新表，回归风险集中在同步层

Storage RLS 与桶策略配错的两个方向：客户文件泄露，或 Miranda 传不了文件
storage.objects 策略用 (storage.foldername(name))[1]::uuid 判工作区，路径拼错、桶误设 public、或 owner_id 列名用错（Supabase 已弃用 owner 改 owner_id）都会让策略静默失效；anon key 公开在仓库里，桶一旦 public 等于合同/报价对全网可下载。反方向：delete 策略叠了 can_edit_project 就会让 Miranda 传不了自己负责客户的文件，功能直接废。
缓解：蓝图 E4-S1 的三账号实测必须做且结果写进 README；桶创建时截图确认 public 未勾；上传路径由 upload.ts 单点生成不允许调用方传 path；上线前用 curl 带 anon key 直接请求一个对象 URL 验证 401；files 表与 storage.objects 的 delete 策略都只用「上传者或 owner」，绝不叠 can_edit_project。
D1/D2 把新对象放宽为成员全可写，与 README「按项目分权」承诺和 Sara 要求 1 的口径冲突
蓝图推荐 clients / 客户级 docs / files 成员全可读写、Miranda 可建 ops campaign，理由充分（否则功能对 Miranda 是废的），但 Sara 提的第一条要求是「由她分配后可修改」。如果没拍板就实施，Sara 事后发现 Miranda 能改任何客户档案、删自己传的文件、建项目，会觉得权限失控；如果按严格口径做，Miranda 的日常闭环全部卡在 Sara 手里。
缓解：把 D1/D2 作为第一阶段开工前必须回答的两个问题单独发给 Sara，附一句话后果对比；实施时 RLS 与 README 权限表同一个 commit 改，权限表里加「客户 / 文档 / 文件」三行。删除动作统一「创建者或 owner」，写动作统一「工作区成员」，不要出现第三种口径。
Service Worker autoUpdate + 每小时 update() 会在 Sara 写 PRD/文档时强制刷新丢内容
vite.config.ts 是 registerType: 'autoUpdate'，新 SW 激活即 reload；E1-S3 加了每小时 r.update() 和 visibilitychange 检查后，触发频率从「只在打开时」变成「随时」，MdEditor 800ms 防抖窗口内的输入和 contentEditable 标题会丢。
缓解：改 registerType: 'prompt'，onNeedRefresh 用现有 toast 显示「有新版本，点击刷新」，只在用户点击或 visibilityState 变 hidden 时执行 updateSW；或 update() 只在 document.hidden 时调用。
Miranda 账号现状未核实，E1-S2 与 D7 的顺序错了会把她锁在空工作区或锁在门外
maps.json 三位读者都问「Miranda 是否已经注册」。若她已用其他邮箱或先于邀请注册，loadMembership 改造前她永远看到空工作区；若 D7 先关闭注册再邀请，她根本注册不了。
缓解：开工第一步在 Supabase 后台查 auth.users 与 workspace_members 确认 Miranda 状态；顺序固定为：loadMembership 改造上线 → 确认 Miranda 在 Sara 工作区 → 关闭注册；README「第一次使用」按此顺序改写。
